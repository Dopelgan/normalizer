# Parser — сервис нормализации документов

Принимает идентификаторы файлов из общего S3, отсеивает то, что не относится
к корпоративным знаниям, проверяет техническую пригодность, разбирает
утверждённое самой дешёвой достаточной стратегией и отдаёт фрагменты RAG в
формате `document_metadata + fragments`.

Интерфейс описан в контракте RAG ↔ Parser: три внутренние ручки,
синхронная и фоновая обработка, результат забирается поллингом.

**Поддерживаемые типы:** PDF, JPG, JPEG, PNG, TIFF, TIF, BMP, DOCX, TXT, CSV,
MD, XLSX, DXF. DWG опознаётся, но отклоняется с объяснением: это закрытый
двоичный формат, для него нужен внешний конвертер в DXF.

                     │  POST /internal/v1/intake      (приём пакета)
                     ▼
        ┌────────────────────────┐
        │  DATA GATEWAY (HTTP)   │  202 + request_id, работы не делает
        └───────────┬────────────┘
                    │ Celery, очередь intake — по задаче на файл
                    ▼

        │  DATA GATEWAY          │  относится ли это к знаниям
        │  G-1 признаки файла    │

        │  G-3 изображения       │  ─── отказ ─────▶ отчёт с причиной
        │  G-4 спорные случаи    │

MinerU работает в режиме `pipeline` (PDF-Extract-Kit: отдельные модели под
layout, OCR, формулы и таблицы). Чертежи через него не идут — у них своя
ветка: геометрия размечает лист, внешняя модель Qwen3-VL его читает.

```
   лист чертежа (скан, фото, картинка в PDF)
            │
            ▼
   ┌──────────────────────────┐   numpy + PIL, без GPU
   │ drawing_vision           │   выравнивание наклона, рамка формата,
   │ «где что лежит»          │   сетки штампа и таблиц, нарезка областей
   └────────────┬─────────────┘
                │  лист + области
                ▼
   ┌──────────────────────────┐   HTTP в контейнер vllm или на свой хост,
   │ модель (QWEN_ENDPOINT)   │   vLLM, OpenAI-совместимый /v1
   │ «что там написано»       │   лист целиком + каждая область отдельно
   └────────────┬─────────────┘
                │  надписи, графы штампа, строки таблиц
                ▼
   ┌──────────────────────────┐   те же правила, что и у векторного листа
   │ правила ГОСТ             │   категория, допуск, единица, характер размера
   │ «проверить и разложить»  │   спор с моделью понижает уверенность
   └──────────────────────────┘
```

**Текстовый слой — источник истины по тексту.** MinerU в режиме `pipeline`
рендерит страницу в растр и читает только то, что layout-модель признала
текстовой рамкой: мелкий светло-серый текст по контрасту туда не попадает,
код в серой заливке размечается как рисунок, а распознанное приходит с
подменами похожих букв (`rps` -> `грs`, `expires_at` -> `exрires_at`). У
векторного PDF всё это уже лежит в файле, поэтому `core/providers/text_layer.py`
читает слой напрямую и сшивает его с рамками MinerU по координатам:

* текст блоков берётся из слоя, а не из распознавания;
* строки, не попавшие ни в одну рамку, возвращаются отдельными фрагментами —
  именно так вернулись потерянные целиком страницы;
* значения ячеек таблиц выправляются по слою (структуру по-прежнему строит
  MinerU);
* у скана слоя нет, и конвейер честно остаётся на OCR.

На контрольном документе (24 страницы, смешанная вёрстка: серые цитаты,
листинги кода в заливке, таблицы) полнота выросла с 68% до 100%, страниц,
потерянных целиком, стало ноль, подмены алфавитов исчезли.

## Приём документов

Два сервиса перед нормализацией, порядок жёсткий.

**Data Gateway** отвечает на вопрос «относится ли это к корпоративным
знаниям». Четыре слоя от дешёвого к дорогому: формальные признаки (тип,
размер, путь, имя), быстрый классификатор категории, отдельная
классификация изображений, разбор спорных случаев основной моделью.

**Quality Gate** отвечает на вопрос «пригоден ли документ технически»:
валидация и открываемость, точные и почти-дубликаты, дата и актуальность,
быстрая проверка читаемости, классификация и предложение размещения.

Смешивать эти вопросы нельзя: личная фотография технически безупречна и
проверку качества прошла бы. Поэтому отсев строго предшествует ей.

**Приём идёт на очереди, а не в HTTP-запросе.** Ручка
`POST /internal/v1/intake` проверяет тело, ставит по задаче на файл в очередь
`intake` и отвечает `202` — вердикты забираются по
`GET /internal/v1/intake/results/{request_id}`.

Так сделано после конкретного случая: пятьдесят PDF без текстового слоя не
уложились ни в таймаут между Data Gateway и Quality Gate (120 с), ни в
таймаут внешнего потребителя (60 с). Потребитель, не дождавшись ответа,
начинал слать запрос заново — и конвейер получал ту же пачку по второму
кругу, поверх ещё не законченной первой. Таймауты можно поднимать (их и
подняли — до 600 и 300 секунд), но это отодвигает границу, а не убирает её:
следующий набор файлов будет тяжелее. Теперь границы нет: ответ отдаётся
сразу, файл обрабатывается столько, сколько нужно, а повторный запрос по
незавершённому `request_id` возвращает `409`, а не запускает вторую
обработку.

Заодно исчез сетевой запрос между сервисами: оба этапа идут в одной задаче
(`core/intake/pipeline.py`), по файлу за раз. Тяжёлый скан задерживает
только себя — вердикты по остальным файлам уже лежат в состоянии запроса.

Приём и разбор разведены по разным очередям и разным воркерам. Приём лёгкий
(чтение, открытие формата, быстрый OCR двух страниц) и идёт в несколько
потоков; разбор занимает GPU и идёт по одному документу. В общей очереди
пачка сканов ждала бы чертёж, который внешняя модель читает минутами.

**Цепочка по-прежнему останавливается на приёме**, но теперь это настройка,
а не закомментированный вызов: `INTAKE_FORWARD_TO_PARSER=false` (по
умолчанию) означает, что `POST /internal/v1/parse/background` не вызывается
и `forwarded` в результате остаётся `false`. Включается переменной окружения,
без правки кода.

Прямой синхронный вход остался для ручной проверки и для установок без
очереди: `POST /internal/v1/intake/sync` у Data Gateway и
`POST /internal/v1/quality` у Quality Gate. На тяжёлых файлах они упираются
в те же таймауты — поэтому штатный вход не там.

**Исходов три, а не два.** Принять, карантин, отклонить. Карантин — не
роскошь: без него система либо пропускает мусор, либо молча теряет нужные
документы. В карантин уходят личные области хранилища (там встречаются
единственные экземпляры документов), спорные случаи и документы, которые
не читаются. Очередь карантина и решения по ней — в ручках ниже.

Решения администратора копятся, и по ним система **предлагает** поправить
правило отсева. Предлагает, а не меняет молча.

Классификатор приёма (`CLASSIFIER_ENDPOINT`) необязателен: когда он не
настроен, решают правила из профиля. Конвейер обязан работать без ML-сервиса.

**Тип файла определяется по содержимому.** Расширение — утверждение
отправителя: `s3_fileid` приходит без него, скан бывает переименован в
`.pdf`, выгрузка отдаёт `.xlsx` с CSV внутри. `core/filetypes.sniff` читает
сигнатуру (pdf, png, jpg, tiff, bmp, dxf, dwg, а docx и xlsx различает по
составу zip) и `resolve` отдаёт фактический тип вместе с объявленным.
Расхождение не молчит: оно попадает в сигналы приёма (`type_mismatch`), в
предупреждения Quality Gate и в лог разбора. От типа зависит род содержимого,
а от рода — какой уровень лестницы возьмётся за документ, поэтому
`DocumentContext` уточняет тип, как только байты прочитаны, а `FileLocator`
для ключа без расширения смотрит первые 8 КБ вместо прежнего «считаем, что
pdf».

**Категория определяется по тексту документа, а не по его байтам.** Слой G-2
достаёт текст инструментом формата (`core/gateway/text_probe`: PyMuPDF для
PDF, python-docx, openpyxl, декодирование для текстовых), и маркеры ищутся по
границам слов. Раньше маркеры искали прямо в первых 64 КБ файла,
декодированных как cp1251: для PDF это сжатый поток, и приложение к договору
было признано перепиской из-за случайной последовательности байтов `re:`
внутри потока. Если текста нет (скан, картинка, чертёж), решает путь — но с
меньшей уверенностью, и переписку по одному пути не объявляют: каталог
«Договоры и ДС» говорит о деловом документе, а о переписке не говорит ничего.
В сигналах видно, чем решено (`matched_in`: текст или путь), какой маркер
сработал и откуда взялся текст (`text_source`).

**Категорию решает счёт по весам, а не первый сработавший маркер.** Словари
и счёт живут в `core/gateway/rules.py`. У каждого маркера своя цена: слово,
которое само называет род документа («договор», «чертёж», «лицензия»), весит
вдвое больше признака, встречающегося и в чужих документах («акт», «график»,
«деталь»). Повторы поднимают вес по логарифму — дюжина «договоров» весомее
одного «сборочного», но не в двенадцать раз. Уверенность берётся из отрыва
лидера от второго места: документ, в котором поровну признаков договора и
чертежа, классификатором не опознан и уходит на разбор спорных случаев
(G-4), а не объявляется тем, чей маркер оказался выше в списке кода. Счёт по
категориям и сработавшие маркеры попадают в сигналы приёма (`rule_scores`,
`rule_hits`) — решение можно проверить, а не принять на веру.

Служебное письмо с исходящим номером считается **деловым документом**, а не
перепиской: оно регистрируется и подшивается в дело наравне с приказом.
Категория «переписка» оставлена почтовым веткам и выгрузкам из мессенджеров
(`Re:`, `Кому:`, «пересланное сообщение»).

**Какие форматы принимаются.** PDF, изображения (png, jpg, tiff, bmp), DOCX и
DOC, таблицы (XLSX, XLSM, XLS, ODS, CSV), текст (TXT, MD) и DXF. Excel
97-2003 читается через `xlrd`, ODS — штатным разбором `content.xml`, книга с
макросами (XLSM) ничем не отличается от XLSX. Формат опознаётся по
содержимому, поэтому `.xls`, пересохранённый под именем `.xlsx`, разберётся
правильно. DWG опознаётся, но не поддерживается: отказ приходит с
объяснением, чем файл конвертировать, а не падением в середине конвейера.

**DOC разбирается через конвертацию в DOCX.** Word 97-2003 — двоичный
формат; всё, что умеет питон без посторонней помощи, — вытащить из него
плоский текст, потеряв таблицы, а таблицы в этих документах и есть
содержание. Поэтому файл один раз конвертируется LibreOffice
(`core/providers/office_convert.py`), и дальше конвейер работает с ним как с
любым DOCX: проба текста на приёме, проверка открываемости, второй уровень
лестницы. Конвертация кешируется по хешу содержимого — один файл за обработку
открывают трижды. Если LibreOffice в образе нет, формат отклоняется на приёме
с внятной причиной, а не падает посреди разбора (`DOC_CONVERT_ENABLED`,
`SOFFICE_BIN`, `DOC_CONVERT_TIMEOUT`).

**Изображение судится по листу, а не по образцу байтов.** Правила слоя G-3
работают на целиком декодированной картинке: у png и jpg в 64 КБ умещался
весь файл, а у bmp и tiff — только заголовок, и один и тот же чертёж
проходил приём по-разному в зависимости от формата хранения. Род листа
определяет `core/providers/raster_drawing` по геометрии: рамка формата,
длинные линии, полосы строк, плотность графики. У модуля есть ответ
«разрешение не позволяет судить» — картинка 80x50 уходит человеку, а не
объявляется чертежом. Скан страницы текста — своя категория `document_scan`,
он принимается наравне с чертежом. Имя файла остаётся подсказкой второго
порядка: «личное_отпуск.jpg» с чертежом на листе не принимается молча, но и
не отклоняется — противоречие решает человек.

## Пределы распознавания

Полный OCR — фоллбэк: он включается, когда MinerU недоступен или у скана нет
текстового слоя. У него три потолка, и все три настраиваются:

| Настройка | Зачем | По умолчанию |
| --- | --- | --- |
| `OCR_FULL_MAX_PAGES` | сколько страниц распознавать; усечение уходит в `degraded` | 50 |
| `OCR_BATCH_PAGES` | размер пачки рендера — страницы не держатся в памяти все сразу | 5 |
| `OCR_MAX_SIDE` | потолок длинной стороны листа: скан A3 в 6600 px распознаётся минутами, а строки читаются не лучше | 3500 |

Раньше потолков не было вовсе: `convert_from_path` разворачивал в память весь
документ, и техническое задание на несколько сотен листов обрывало воркер
до первой распознанной строки.

Отдельное правило про недоступный MinerU: она запоминается на минуту, и
уровень 5 (разметка) на это время пропускается. Иначе он вызывал тот же
полный OCR, который уже сделал уровень 4, — вдвое дольше и без единого
нового символа.

## Лестница стратегий

До разбора документ классифицируется по источнику (есть ли исходник САПР,
есть ли текстовый слой, только растр), по роду (чертёж, таблица, текст,
смешанный) и по пригодности растра. Дальше маршрутизатор начинает с самой
дешёвой применимой стратегии и поднимается выше, пока уверенность или
структурная полнота ниже порога.

| Уровень | Стратегия | Когда применима | Стоимость |
|---|---|---|---|
| 1 | Чтение исходника САПР (DXF) | Есть исходник | Минимальная, результат точный |
| 2 | Текстовый слой PDF, DOCX, TXT, MD | Содержимое лежит в файле текстом | Низкая |
| 3 | Табличный разбор XLSX и CSV | Таблица жёсткого формата | Низкая |
| 4 | Распознавание без структуры | Растр приемлемого качества | Средняя |
| 5 | Детекция областей (MinerU) | Сложная структура, чертёж | Высокая |
| 6 | Восстановление растра плюс 5 | Растр низкого качества | Наивысшая |
| 7 | Мультимодальная модель | Неоднозначность после 5 или 6 | По фрагментам |

**Результаты уровней не смешиваются.** Каждый уровень даёт свой результат
целиком, они сравниваются оценкой, наружу уходит лучший. Как он выбран —
видно в `ladder` сырого результата парсера: классификация, все попытки, их
оценки и причина подъёма.

Ключевая деталь оценки: текстовый слой даёт идеально точный текст, но про
таблицы и чертежи не знает ничего. Поэтому структурная неполнота
наказывается отдельно от уверенности — иначе лестница останавливалась бы на
уровне 2 для любого документа. Простой текстовый PDF на нём и
останавливается, экономя весь тяжёлый конвейер.

**Фоллбэк подъём не останавливает.** Распознавание без структуры (уровень 4)
на плотной странице легко набирает балл выше порога — просто потому, что
символов много. Но ни таблицу, ни формулу, ни поле чертежа этот уровень
вернуть не может, и остановка на нём означала, что лист с формулами уезжал в
индекс абзацем вида `д = —fz+ay`.

**Структурный разбор старше фоллбэка всегда, а не только выше порога.**
Оговорка про порог оставляла дыру ровно там, где она дороже всего. На скане
с формулами Tesseract набирал 0.87 объёмом каши, а разбор с детекцией
областей — 0.39, потому что формулы дают мало символов: старшинство
кончалось у порога, и наружу уходила каша. Балл меряет объём текста и
уверенность, то есть ровно те величины, по которым каша выглядит хорошо, и
решать им спор между разными способами разбора нельзя. Порог теперь решает
только, останавливаться ли лестнице.

Оговорка одна и она про сохранность: структурный результат получает
старшинство, только если принёс сопоставимый объём текста —
`LADDER_CONTENT_KEEP_RATIO` (по умолчанию 0.5) от лучшего фоллбэка. Разбор,
вернувший три символа со страницы, не побеждает распознавание всей страницы
просто по признаку «структурный».

**Победивший фоллбэк — это деградация.** Если структурный уровень отработал
и всё равно проиграл, документ помечается: запись уходит в
`parse_result.degraded`, в `documents.extra_data.fallback_won`, в лог уровня
ERROR, а все фрагменты получают `needs_review`. Раньше такой документ
выглядел нормально разобранным: полнота OCR-страницы 0.72 при пороге 0.5
флага не давала.

**Недоступность MinerU — не свойство документа.** Лежащий `mineru-api` не
роняет ни один запрос, и без отдельной пометки его невозможно отличить от
плохого скана: приём «работает», качество падает молча и на всём потоке
сразу. Теперь это `degraded: ["mineru_unavailable: ..."]`, ERROR в логе и
`needs_review` на всех фрагментах документа.

**Отчёт о выборе уровня — рядом с документом.** `documents.extra_data`
хранит `chosen_level`, `chosen_strategy`, `ladder_attempts` (уровень,
стратегия, балл, объём текста, фоллбэк ли), `fallback_won` и `degraded`.
Полный отчёт по-прежнему лежит в `ladder` сырого результата парсера.

Ненужные уровни отключаются профилем (`LADDER_ENABLED_LEVELS`), без правки
кода.

## API

Все ручки доступны только внутри docker-сети. Авторизации в MVP-контракте нет,
поэтому наружу порты публиковать не следует (в compose порт привязан к
`127.0.0.1` для ручной проверки).

### Приём пакета (вход всей цепочки)

```http
POST /internal/v1/intake
```

```json
{
  "request_id": "req-1",
  "files": [
    {"s3_fileid": "регламент.pdf", "operation": "create"},
    {"s3_fileid": "чертёж-ревизия-2.pdf", "operation": "update"},
    {"s3_fileid": "личное/отпуск.jpg", "operation": "create"}
  ]
}
```

Операция принадлежит файлу, а не пакету: в одном приёме приходят и новые
документы, и обновления уже принятых. `dialog_id` на приёме нет — цепочка
приёма его не использует; в ручках `/internal/v1/parse*` он остался.

Один и тот же `s3_fileid` дважды в пакете — `422`: неясно, какую операцию по
нему выполнять. Потолок размера пакета — `INTAKE_MAX_FILES`.

Ответ — `202`, работа идёт в очереди:

```json
{
  "request_id": "req-1",
  "accepted": true,
  "status": "queued",
  "total": 3,
  "poll_url": "/internal/v1/intake/results/req-1"
}
```

Повторный запрос по незавершённому `request_id` — `409`. Это важно для
потребителя, у которого истёк собственный таймаут: повтор не должен
запускать вторую обработку поверх первой.

### Результат приёма

```http
GET /internal/v1/intake/results/{request_id}
```

```json
{
  "request_id": "req-1",
  "status": "completed",
  "total": 3,
  "processed": 3,
  "accepted": ["регламент.pdf"],
  "quarantined": ["чертёж-ревизия-2.pdf"],
  "rejected": ["личное/отпуск.jpg"],
  "verdicts": [{"s3_fileid": "регламент.pdf", "outcome": "accept",
                "stage": "data_gateway", "layer": "G-2",
                "category": "business_document", "confidence": 0.9,
                "reason": "..."}],
  "files": [{"s3_fileid": "регламент.pdf", "outcome": "accept",
             "verdicts": [],
             "timings_ms": {"intake.file": 1840.2,
                            "data_gateway.read": 12.4,
                            "quality_gate.readability": 1502.7}}],
  "forwarded": false
}
```

`status` — `queued`, `processing` или `completed`. Списки `accepted`,
`quarantined`, `rejected` и `verdicts` те же, что были в синхронном ответе:
потребителю, который их уже разбирает, менять разбор не придётся — меняется
только момент получения. Новое здесь — `files[].timings_ms`: время каждой
операции по конкретному файлу.

`404` — приёма с таким `request_id` не было или истёк
`INTAKE_STATE_TTL_SECONDS`.

Остальные ручки приёма:

```http
POST /internal/v1/intake/sync                     приём без очереди
GET  /internal/v1/intake/quarantine               очередь администратору
POST /internal/v1/intake/quarantine/{id}/resolve  решение по карантину
GET  /internal/v1/intake/report                   отчёт по массовому приёму
GET  /internal/v1/intake/suggestions              что поправить в правилах
GET  /metrics                                     метрики Prometheus
```

### Синхронная обработка

```bash
curl -X POST http://127.0.0.1:8000/internal/v1/parse \
  -H 'Content-Type: application/json' \
  -d '{
    "request_id": "req-001",
    "dialog_id": "dialog-001",
    "s3_fileid": ["file-id-001", "file-id-002"]
  }'
```

`200 OK` с одним элементом `documents` на каждый входной `s3_fileid`.
Если обработка не уложилась в `PROCESSING_TIMEOUT_SECONDS`, вернётся `504`,
а результат останется доступен по `request_id`.

### Фоновая обработка

```bash
curl -X POST http://127.0.0.1:8000/internal/v1/parse/background \
  -H 'Content-Type: application/json' \
  -d '{
    "request_id": "req-002",
    "dialog_id": "background-dialog-001",
    "operation": "create",
    "s3_fileid": ["file-id-003"]
  }'
```

`202 Accepted`, `status: queued`. `operation` принимает `create` или `update`;
`update` переобрабатывает документ, даже если он уже проиндексирован.

Тело принимается и в виде списка файлов со своими операциями — так присылает
Quality Gate, и `dialog_id` в нём необязателен:

```json
{
  "request_id": "req-002",
  "files": [
    {"s3_fileid": "file-id-003", "operation": "create"},
    {"s3_fileid": "file-id-004", "operation": "update"}
  ]
}
```

Когда операции у файлов разные, общей операции у пакета нет, и в ответе
`operation` приходит `null`.

### Получение результата

```bash
curl http://127.0.0.1:8000/internal/v1/parse/results/req-002
```

`status`: `queued` → `processing` → `completed` (либо `partial`, если часть
файлов не обработалась, либо `error`, если не обработался ни один).
Результат хранится `RESULT_TTL_SECONDS` (по умолчанию сутки).

### Формат фрагмента

```json
{
  "fragment_id": "doc-001-frag-001",
  "type": "text",
  "content": {
    "text": "Нормализованный текст",
    "table_data": null,
    "image_ref": null,
    "formula_mathml": null,
    "parsed_expression": null,
    "structured_drawing_fields": null,
    "structured_payload": null
  },
  "position": {"page": 1, "sheet": null, "bbox": [0.1, 0.2, 0.9, 0.3], "order": 1},
  "section_title": null,
  "confidence": 0.97,
  "completeness": 1.0,
  "provenance": {"method": "text_layer_extraction", "strategy_level": 2, "source": "vector_pdf"},
  "graph_nodes": [],
  "relations": []
}
```

Все поля присутствуют всегда, даже со значением `null`. `bbox` нормализован
в диапазон `[0, 1]`. Поля доступа (`container`, `legal_entity`, `sensitivity`)
Parser не формирует.

**Порядок фрагментов — порядок документа.** `position.order` сквозной по
документу и расставлен по месту блока-источника: для таблицы, формулы,
чертежа и картинки это сам блок, для текста — первый блок куска. Поэтому
нарезка получает текстовые блоки не одним списком, а цепочками подряд идущих:
склеивать абзацы через стоящую между ними таблицу нельзя — склейка встаёт на
место своего первого блока, и таблица уезжает за неё.

### Как считаются confidence и completeness

| Тип        | completeness                                                       |
|------------|--------------------------------------------------------------------|
| `text`     | доля символов текстового слоя, доехавшая до фрагментов (векторный PDF); для скана — доля площади листа, покрытая блоками, ×0.8 для OCR-фоллбэка, ×0.9 если координат нет |
| `table`    | доля заполненных ячеек                                             |
| `formula`  | 0.5 за текст, +0.3 за MathML, +0.2 за разобранное выражение         |
| `image`    | 1.0, если изображение извлечено                                     |
| `drawing`  | доля полей, отнесённых к конкретной категории (`note` = не разобрано) |

Фрагменты ниже `COMPLETENESS_THRESHOLD` помечаются в БД
(`chunks.extra_data.needs_review`); в контракт эта пометка не входит, наружу
деградация видна через `completeness`.

`provenance.method` отражает фактический путь блока, а не его тип:
`text_layer_extraction` (уровень 2) ставится только тому, что действительно
прочитано из слоя, распознанное MinerU — это `mineru_ocr` (3), векторный
чертёж — `vector_text_layer` (4). Растровый чертёж, прочитанный внешней
моделью, — это `vision_plus_vlm` (7), а если разметка зрением была выключена
или ничего не нашла — `vlm_full_page` (7).

Уверенность поля чертежа складывается из согласия модели с правилами ГОСТ:
совпали категории — 0.9, правила такой категории не знают (номер позиции,
графа штампа) — 0.75, разошлись — 0.6, поле читалось в найденной области —
0.85. Выдуманная моделью категория в контракт не попадает: её заменяет
категория по правилам.

## Где Parser ищет файлы

RAG передаёт только `s3_fileid`. Parser строит путь как
`SOURCE_PREFIX + s3_fileid` внутри хранилища (`STORAGE_TYPE=local` — от
`STORAGE_LOCAL_MOUNT`, `s3` — от `S3_BUCKET`). Если идентификатор пришёл без
расширения, перебираются известные (`.pdf`, `.png`, `.docx`, …).

## Что Parser пишет и куда

S3 выдан только на чтение, поэтому запись и чтение разведены:

| Что | Куда | Настройка |
| --- | --- | --- |
| Исходные документы | S3, только чтение | `S3_BUCKET`, `SOURCE_PREFIX` |
| Ассеты из PDF, выправленные растры | том сервиса | `ARTIFACTS_MOUNT`, `ASSETS_PREFIX` |
| Сырой ответ парсера (JSON) | том сервиса | `ARTIFACTS_MOUNT`, `RAW_PARSE_S3_PREFIX` |
| Временные файлы (poppler, tesseract) | том сервиса | `TEMP_DIR` |

При `STORAGE_TYPE=s3` и `S3_READONLY=true` (значение по умолчанию) работает
`ReadThroughS3Provider`: `s3://…` читается из бакета, всё остальное читается и
пишется в `ARTIFACTS_MOUNT`. Попытка записать в `s3://` поднимает
`ReadOnlyStorageError` — вместо `AccessDenied` из глубины boto3. В результате
документа URI ассетов и сырого JSON — локальные относительно тома; потребитель
читает их через тот же том.

`TEMP_DIR` выставляется в `TMPDIR`/`TEMP`/`TMP` на старте каждого процесса
(`core.workspace.configure_process_tempdir`), поэтому в том уходит и то, что
пишут подпроцессы — `pdftoppm`, `tesseract`. На слое контейнера временных
файлов не остаётся. Если том не смонтирован, сервис не падает: уходит в
системный каталог и пишет об этом предупреждение.

## Замер времени операций

Повод тот же, что и у очереди: пачка сканов не уложилась в таймаут, а по
логам нельзя было сказать, что именно отняло время — чтение из хранилища,
открытие PDF, быстрый OCR или поиск почти-дублей. Таймаут подняли вслепую.

Теперь у каждого заметного шага есть длительность, и она уходит сразу в три
места.

**В лог.** Строкой на событие, в JSON (`LOG_FORMAT=json`; `text` оставлен
для чтения глазами):

```json
{"ts":"2026-09-20T12:31:02.884Z","level":"INFO","service":"quality_gate",
 "event":"stage","stage":"quality_gate.readability","duration_ms":1502.7,
 "outcome":"accept","file_type":"pdf"}
```

Отобрать всё дороже секунды по одному этапу:

```bash
docker compose logs intake_worker \
  | grep '"event":"stage"' \
  | jq -c 'select(.duration_ms > 1000) | {stage, duration_ms, s3_fileid}'
```

**В ответ и в базу.** `files[].timings_ms` в результате приёма и
`extra_data.timings_ms` у документа: по конкретному файлу видно, где он
провёл время, без похода в логи. Собирает их `core/telemetry.py`:
`telemetry.collect()` открывает область сбора, вложенные `measure` в любых
модулях складывают длительности в неё.

**В метрики.** Гистограмма `normalizer_stage_duration_seconds` с метками
`service`, `stage`, `outcome` и счётчик `normalizer_stage_failures_total`.
У сервисов FastAPI их отдаёт ручка `/metrics`, у воркеров — отдельный порт
`METRICS_WORKER_PORT` (в compose проброшены: разбор — 9100, приём — 9101).

Без `prometheus-client` сервис работает: тайминги остаются в логах и в
ответе, пропадают только метрики. Замер не имеет права ронять обработку —
ошибка внутри него не подменяет собой ошибку измеряемого кода.

Что меряется:

| Этап | Где |
| --- | --- |
| `intake.file` | приём одного файла целиком |
| `data_gateway.read`, `.content_layer`, `.image_layer`, `.escalation` | слои отсева |
| `quality_gate.read`, `.technical`, `.duplicates`, `.freshness`, `.readability`, `.routing` | этапы проверки пригодности |
| `convert.office` | конвертация `.doc` в `.docx` |
| `parse.locate`, `.document`, `.normalize`, `.drawings`, `.file_hash`, `.save` | разбор документа |

## Известные ограничения

**Чертежи: два разных случая.**

*Векторный лист из CAD* обрабатывается без распознавания вовсе.
`vector_drawing.detect_drawing_pages` относит страницу к чертежам по её
собственной геометрии — плотность векторов, рамка формата, сетка штампа в
правом нижнем углу по ГОСТ 2.104, — а поля собираются из текстового слоя,
включая повёрнутые подписи размеров, которые в растре теряются. Значения
берутся из файла как есть, поэтому `confidence` поля — это уверенность в
*категории*, а не в тексте. Провенанс таких полей — `vector_text_layer`.

*Сканированный лист* (скан, фотография, картинка внутри PDF) читает внешняя
модель, а размечает его геометрия. Порядок такой:

1. `drawing_vision` выправляет наклон, находит рамку формата, штамп в правом
   нижнем углу и таблицы по сеткам линий. Только numpy и PIL — ни GPU, ни
   обучения, ни новых зависимостей.
2. Лист целиком уходит в Qwen3-VL, следом каждая найденная область отдельным
   запросом с увеличением: мелкий текст штампа на увеличенном фрагменте
   читается заметно лучше, а лист в таком разрешении не отправить.
3. Прочитанное приводится к записи по ГОСТ (`drawing_text`: `⌀`, `±`,
   кириллические гомоглифы в посадках и резьбе) и проверяется теми же
   правилами, что и векторный лист.

**Почему так, а не детектором.** Прогон шести способов на настоящем листе:
сплошное распознавание листа давало 11 надписей из 46 при 85% мусора и ни
одной строки спецификации; нарезка таблиц по найденной сетке подняла их
чтение до 73% словесных полей; мультимодальная модель прочитала 45 из 46 без
единой выдумки. Ни один способ не самодостаточен — зрение находит, модель
читает, правила проверяют.

**Чего ветка не делает.** Связи «размер относится к этому элементу» здесь
нет, поэтому полнота — это доля полей, которым нашлась категория, а не
единица. Выносок, кружков позиций и знаков шероховатости геометрия не ищет:
на живом листе это давало 26 ложных кружков и 116 ложных полок, а модель
читает эти надписи и так.

**Таблица составных частей не помещается в контракт.** Полей вида «строка
спецификации» в нём нет, поэтому прочитанные таблицы уходят целиком в
`content.structured_payload.tables` (там же `layout` — что нашла геометрия,
`title_block` — графы штампа, `sheet_type` и имя модели). Это открытый
вопрос к контракту, а не обход: раскладывать спецификацию по `note` значило
бы засорять индекс.

**Время на лист ограничено.** Запросов к модели на один лист несколько (сам
лист плюс области), и при неудачном сочетании таймаутов они переживают
`CELERY_TASK_TIME_LIMIT`, а тогда теряется весь результат, а не часть.
`DRAWING_TIME_BUDGET` (по умолчанию 420 с при пределе задачи 600 с)
останавливает чтение областей: штамп читается первым, пропущенное
отмечается в `structured_payload.regions_skipped`.

**Без модели ветка молчит.** Если `QWEN_ENDPOINT` пуст или хост не отвечает,
чертёж остаётся неразобранным: фрагмент не превращается в `drawing`, причина
уходит в лог. Сплошное распознавание листа как замена убрано намеренно —
24% попаданий при 85% мусора хуже, чем честное «не разобрано».

**Детектор YOLO и Florence из проекта убраны.** Стоковый `yolo11m-obb.pt`
обучен на аэроснимках DOTA, категорий чертежа не знает и возвращал ноль
областей, из-за чего лист доезжал до сплошного OCR. Клиенты, сервисы,
образы, настройки и каркас дообучения удалены целиком — вернуть их можно
из истории git, когда появятся веса под ЕСКД.

Сам лист-картинка до ветки доходит. Раньше разбор чертежей включался только
на вложенном фрагменте `image`, которого в документе-скане нет: картинка и
есть документ, и чертёж молча разбирался как страница текста.

Единица измерения и признак справочного размера больше не подставляются по
умолчанию: неизвестное остаётся пустым.

**Без PyMuPDF.** Текстовый слой не читается, и конвейер работает как
раньше — на распознавании, со всеми его потерями. Пакет есть в
`requirements.txt`; если он не установлен, в лог уходит предупреждение.

**Формулы.** MinerU отдаёт LaTeX, он попадает в `content.text`.
`formula_mathml` остаётся `null`, `parsed_expression` заполняется только для
выражений вида `X = ...`. Формулы приезжают только с уровня 5: распознавание
без структуры их не видит, и до того, как фоллбэк перестал останавливать
лестницу, лист с формулами до уровня 5 просто не доходил.

**Слой распознавания для растра.** У скана и картинки текстового слоя в
файле нет, но его можно собрать построчным OCR (`rus+eng`) и сшить с
блоками MinerU тем же механизмом, что и слой векторного PDF: структура от
MinerU, текст со стороны. Включается `OCR_LAYER_ENABLED` (по умолчанию да),
стоит одного прохода Tesseract на документ. Метод таких фрагментов —
`ocr_layer`, уровень 5, и уверенность у них своя, из распознавания: выдавать
распознанное за текст из файла нельзя, на этой уверенности стоит выбор
уровня лестницы.

**Русский текст в ячейках таблиц.** Модель таблиц MinerU отдаёт содержимое
ячеек в LaTeX. Для колонки с формулами это верно, для колонки с прозой —
нет: русское описание превращается в побуквенную разметку вида
`\mathsf { c } \mathsf { K } \mathsf { O } ...`, из которой исходную строку
не восстановить — буквы потеряны при распознавании, а не при разметке.
Такие ячейки узнаются по частоте переключения гарнитуры или по длинной
цепочке одиночных букв (`core/providers/latex_text.py`; второй признак
самостоятелен — строка вида `A K T T E X H M \in C K O ...` разметки почти
не несёт, а формулой не является) и заменяются текстом строк OCR: колонки
берутся по вертикальным коридорам пустоты между занятыми отрезками строк,
строка таблицы — по естественным вертикальным разрывам внутри колонки.
Формульные ячейки при этом не трогаются.

Починка засчитывается, только если в сетку доехали слова строк: заполнить
все испорченные ячейки мало — строка, отнесённая не к той колонке, попадает
в клетку, которую никто не чинит, и пропадает совсем. Порог — 90% слов
длиннее трёх букв.

Если геометрия не сошлась с формой, которую заявила таблица, или в ячейки
доехало не всё, таблица разбирается на части: формульные ячейки уходят
фрагментами `formula`, проза — текстовыми фрагментами из строк OCR, а сама
таблица остаётся без разбора с картинкой области и нулевой полнотой, то
есть с `needs_review`. Заполнять ячейки наугад или отдавать разметку в
индекс хуже любого из этих исходов. Счётчики — в `text_layer_stats`:
`mangled_tables`, `repaired_tables`, `degraded_tables`.

**Русский текст в формульных блоках.** Та же беда вне таблиц: модель формул
MinerU заворачивает в LaTeX любую строку, которую сочла формулой, и на
скане так уезжает заголовок листа целиком — `\mathsf { A K T T E X H M 4 E
C K O P O O C M O T P A }` вместо «АКТ ТЕХНИЧЕСКОГО ОСМОТРА». Блок с такой
разметкой перестаёт быть формулой: текст берётся из строк слоя, попавших в
его рамку, метод — `ocr_layer`. Если строк в рамке нет, снимается разметка,
блок помечается фоллбэком и уезжает на проверку, а в `degraded` появляется
`formula_not_text`. Счётчики: `mangled_formulas`, `repaired_formulas`,
`decoded_formulas`.

**Продолжение многостраничной таблицы.** MinerU отдаёт такую таблицу целиком
в рамке первой страницы, а дальше присылает пустые рамки без разбора и без
картинки. Строки слоя внутри пустой рамки — это те же данные во второй раз,
уже без колонок: они гасятся, если их слова находятся в разобранных
таблицах документа (порог 80% слов длиннее двух букв), а рамка, из которой
после этого нечего доставать, из выдачи убирается. Счётчики:
`duplicate_lines`, `dropped_empty_tables`.

**content_list без координат.** Если MinerU вернул только `content_list`
(без `middle_json`), координат блоков нет — `bbox` будет на весь лист, и
полнота текстовых фрагментов понижается на 10%, чтобы метрика не выглядела
достовернее, чем есть.

**Параллельная обработка одного файла.** Если два запроса пришли на один
`s3_fileid` одновременно, документ обработается дважды: свой ответ должен
получить каждый `request_id`. Запись в БД защищена `SELECT ... FOR UPDATE`,
дублей фрагментов не возникает.

## Безопасность

**Модель угроз.** Контур считается доверенным: сервис стоит во внутренней сети,
наружу не публикуется ни одна ручка, и единственный, кто до них ходит, — свой
же бэкенд. Всё, что ниже, читается с этой оговоркой; при выносе сервиса в
чужую сеть список принятых рисков придётся пересматривать целиком.

Что закрыто:

- ML-сервисы изолированы в сети `internal_net` без выхода в интернет.
- Исключение одно: воркер подключён ещё и к `public_net`, потому что модель
  чертежей живёт в своём контейнере или на отдельном хосте. Если он в своей
  сети, в `docker-compose.yml` у `celery_worker` меняется именно эта запись.
- `LocalStorageProvider` защищён от path traversal (`Path.is_relative_to`).
- Секреты берутся из `.env`, который не коммитится.
- Порты `postgres`, `redis`, `minio` и API привязаны к `127.0.0.1`.
- Потолки на размер файла и пакета стоят до чтения файла в память; у Pillow
  задан `MAX_IMAGE_PIXELS` — декомпрессионная бомба не проходит.
- Контейнеры приложения работают от пользователя `app` (UID 1000), исходники
  смонтированы на чтение: сбой в коде не переписывает рабочую копию на хосте.

Принятые риски — решение осознанное, не недосмотр:

- **Авторизации на ручках нет.** Опаснее прочих
  `/internal/v1/intake/quarantine/{id}/resolve`: он подменяет обучающий
  сигнал, и тому, кто попал во внутреннюю сеть, этого хватит. Защита —
  только сетевая. Публиковать порты наружу нельзя.
- **Пароли в `config.py` и compose — значения для стенда.** `secure_password`,
  `minioadmin` и Redis без `--requirepass` годятся, пока БД и брокер слушают
  `127.0.0.1` и живут в `internal_net`. Любое окружение, где это не так,
  начинается с правки `.env`.

### Боевой образ

`Dockerfile.dev` рассчитан на горячую правку: код монтируется с хоста.
`Dockerfile.prod` собирает образ с кодом внутри — компилятор остаётся в
промежуточном слое, ничего не монтируется, пользователь тот же `app`. В
compose он подставляется заменой `dockerfile:` у четырёх сервисов
приложения; монтирования `./core`, `./ingest`, `./gateway`, `./quality` при
этом убираются.

Том `shared_data`, созданный до перехода на непривилегированного
пользователя, остаётся за root. Один раз:

```bash
docker compose run --rm --user root celery_worker chown -R 1000:1000 /data/shared
```

## Диагностика

| Симптом | Что смотреть |
|---|---|
| Приём не отвечает вердиктами | это норма: ручка отдаёт `202`, вердикты — по `GET /internal/v1/intake/results/{request_id}` |
| Приём висит в `queued` | поднят ли `intake_worker`: `docker compose logs intake_worker`; очередь должна быть `intake` |
| `409` на приёме | предыдущий приём с тем же `request_id` ещё не закончен — заберите результат или смените `request_id` |
| Непонятно, где файл провёл время | `files[].timings_ms` в результате приёма, `extra_data.timings_ms` у документа, события `"event":"stage"` в логах |
| `.doc` отклоняется | стоит ли `libreoffice-writer` в образе: `docker compose exec intake_worker which soffice` |
| Модель не найдена | `docker compose logs model-downloader`, содержимое `./models` |
| GPU недоступна | `nvidia-smi`, секция `deploy.resources` в compose |
| Задачи не выполняются | `docker compose logs celery_worker`; очередь должна быть `ml_gpu` |
| `status: error` в результатах | поле `error` в документе и логи воркера |
| Пустые фрагменты у скана | установлен ли `tesseract-ocr-rus` в образе |
| Чертёж не разобран | задан ли `QWEN_ENDPOINT`; `curl $QWEN_ENDPOINT/models` из воркера |
| Модель отвечает не-JSON | лог воркера: там первые 200 символов ответа; проверьте, что поднята VL-модель |
| Штамп не найден геометрией | `structured_payload.layout` во фрагменте: рамка, число линий, области |
