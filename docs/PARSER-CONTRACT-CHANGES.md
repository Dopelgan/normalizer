# Изменения контракта Parser

Это согласованное изменение Parser и RAG; локальная реализация не означает, что контракт уже развёрнут на сервере.

## Связь с пачкой lifecycle-событий Backend → RAG

`POST /internal/rag/lifecycle` принимает от Backend `events` из 1–256 элементов (см. `docs/BACKEND-ADMIN-CONTRACT-CHANGES.md`). **Это пачка только на входе RAG.** RAG обрабатывает её поэлементно: для каждого принятого события создаёт отдельную задачу с его `event_id` и `idempotency_key`. Повторное событие не создаёт повторной задачи Parser.

- `asset.created` → фоновый Parser `operation: "create"`;
- `asset.updated`, `asset.restored`, `asset.reprocess_requested` → фоновый Parser `operation: "update"`;
- `asset.deleted`, `asset.withdrawn` обрабатываются в RAG без вызова Parser.

Для одного события, требующего разбора, RAG отправляет **один** `POST /internal/v1/parse/background` с тем же `event_id` и одним значением в `s3_fileid`. `request_id` относится к отдельному запросу Parser. Если входящая пачка содержит несколько таких событий, RAG отправляет несколько независимых запросов Parser; общий batch ID в Parser не требуется. Результат или ответ Parser сопоставляется с исходным событием по `event_id` и с файлом по `s3_fileid`. Для `completed`/`partial` результат содержит ровно один документ с тем же `s3_fileid`. Ошибка или частичный результат одного файла не меняет статус другого элемента пачки.

`asset_id` и `storage_key` из lifecycle-события не переименовывают автоматически в `s3_fileid`: RAG должен передать Parser идентификатор, по которому Parser действительно может прочитать тот же файл, и сохранить соответствие с исходным `asset_id`. Этот маппинг необходимо закрепить интеграционным тестом перед реализацией нового endpoint.

## Главное правило по идентификаторам

- Синхронная обработка `POST /internal/v1/parse`: `dialog_id` оставляем.
- Фоновая обработка `POST /internal/v1/parse/background`: `dialog_id` убираем, используем только `event_id`.
- В фоновой обработке `event_id` связывает lifecycle-событие, запрос Parser и результат Parser.
- `s3_fileid` не переименовываем и не меняем его тип.
- `event_id`, пришедший от Backend, не заменяем новым UUID при постановке отдельной задачи Parser.

## 1. Синхронный контракт — без изменения

### `POST /internal/v1/parse`

```json
{
  "request_id": "parse-123",
  "dialog_id": "dialog-456",
  "s3_fileid": ["cluster-a/document.pdf"]
}
```

`dialog_id` здесь остаётся, потому что синхронный разбор вызывается из пользовательского диалога.

Внутри Parser синхронный разбор может идти в отдельную очередь Celery (`CELERY_INTERACTIVE_QUEUE`, см. README, «Очередь синхронного разбора»), чтобы вложения чата не ждали пакетную переобработку. Контракт ручки от этого не меняется.

Ответ также остаётся в текущем формате:

```json
{
  "request_id": "parse-123",
  "dialog_id": "dialog-456",
  "documents": []
}
```

## 2. Фоновый контракт — убрать `dialog_id`

### `POST /internal/v1/parse/background`

### Было

```json
{
  "request_id": "parser-request-123",
  "event_id": "event-123",
  "dialog_id": "event-123",
  "operation": "create",
  "s3_fileid": ["cluster-a/document.pdf"]
}
```

### Станет

```json
{
  "request_id": "parser-request-123",
  "event_id": "event-123",
  "operation": "create",
  "s3_fileid": ["cluster-a/document.pdf"]
}
```

Изменилось только это поле:

```diff
- "dialog_id": "event-123"
```

В фоне `dialog_id` больше не передаём и не проверяем.

Локальный RAG runtime уже отправляет фоновый `event_id` без технического `dialog_id=event_id`. Совместимость с развёрнутым Parser необходимо подтвердить интеграционным тестом перед включением нового пути; диалоговый Parser-контракт с `dialog_id` остаётся отдельным.

Для Backend-facing `GET /graph` остаётся уточнить семантику Parser `relations`: стабильные ID исходного и целевого объекта, тип направленной связи, fragment ID доказательства и калиброванные `weight`/`confidence`. Локальный Parser-контракт сейчас допускает произвольные словари `graph_nodes`/`relations`; RAG сохраняет их в provenance, но не публикует как доказанные document-document рёбра без этих полей.

### Ответ `202 Accepted`

```json
{
  "request_id": "parser-request-123",
  "event_id": "event-123",
  "operation": "create",
  "accepted": true,
  "status": "queued"
}
```

Из ответа также убирается только `dialog_id`.

## 4. Общее извлечение фактов и значений

### Зачем

RAG должен видеть не только текстовый chunk, но и явно извлечённые значения из любого документа: числа, диапазоны, даты, сроки, единицы измерения, идентификаторы, перечисления и значения из таблиц. Это общий продуктовый контракт, а не набор полей под конкретные демонстрационные вопросы.

В `ParsedFragment` добавить поле `extracted_facts`.

### Пример

```json
{
  "fragment_id": "cluster-a/document.pdf:page-4:block-2",
  "type": "text",
  "content": {
    "text": "Максимальная температура — 80 °C. Допустимый диапазон давления — 0,4–0,6 МПа.",
    "table_data": null,
    "image_ref": null,
    "formula_mathml": null,
    "parsed_expression": null
  },
  "position": {
    "page": 4,
    "sheet": null,
    "bbox": [10, 20, 300, 400],
    "order": 12
  },
  "section_title": "Технические характеристики",
  "confidence": 0.96,
  "completeness": 1.0,
  "provenance": {
    "method": "pdf_text",
    "strategy_level": 1,
    "source": "cluster-a/document.pdf"
  },
  "extracted_facts": [
    {
      "fact_id": "cluster-a/document.pdf:page-4:block-2:fact-1",
      "fragment_id": "cluster-a/document.pdf:page-4:block-2",
      "key": "document.parameter",
      "label": "максимальная температура",
      "value": {
        "kind": "number",
        "raw": "80 °C",
        "number": 80,
        "unit": "°C",
        "operator": "<="
      },
      "confidence": 0.98
    },
    {
      "fact_id": "cluster-a/document.pdf:page-4:block-2:fact-2",
      "fragment_id": "cluster-a/document.pdf:page-4:block-2",
      "key": "document.parameter",
      "label": "допустимый диапазон давления",
      "value": {
        "kind": "range",
        "raw": "0,4–0,6 МПа",
        "min": 0.4,
        "max": 0.6,
        "unit": "MPa",
        "operator": "range"
      },
      "confidence": 0.94
    }
  ],
  "graph_nodes": [],
  "relations": [],
  "structured_drawing_fields": [],
  "structured_payload": null
}
```

Правила для `extracted_facts`:

- `fact_id` стабилен в рамках одного файла и фрагмента;
- `fragment_id` связывает факт с исходным текстом;
- `key` — расширяемый ключ типа факта, без фиксированного списка под один проект;
- `label` сохраняет название параметра так, как оно извлечено из документа;
- `value.kind`: `number`, `range`, `date`, `duration`, `text`, `boolean`, `identifier`, `enum`;
- `value.raw` сохраняет исходную запись;
- `value.number` используется для одного числа;
- `value.min` и `value.max` используются для диапазона;
- `value.unit` хранит единицу измерения, если она есть;
- `value.operator`: `=`, `<=`, `>=`, `<`, `>`, `range`;
- Parser не должен придумывать значение или единицу, которых нет в документе;
- Parser извлекает факт, но не решает, нужен ли он для конкретного пользовательского вопроса;
- для таблиц факты должны сохранять координаты строки и столбца через provenance/structured payload.

## 5. Provenance и стабильные фрагменты

`fragment_id` должен оставаться одинаковым при повторном разборе того же файла.

В provenance добавить:

```json
{
  "method": "pdf_text",
  "strategy_level": 1,
  "source": "cluster-a/document.pdf",
  "source_file_id": "cluster-a/document.pdf",
  "source_page": 4
}
```

Без этого RAG не сможет открыть страницу, показать доказательство числового ответа и обновить старый фрагмент без дубля.

## 6. Частичный результат

Для `status: partial` добавить список обработанных и необработанных страниц:

```json
{
  "request_id": "parser-request-123",
  "event_id": "event-123",
  "operation": "create",
  "status": "partial",
  "documents": [
    {
      "s3_fileid": "cluster-a/document.pdf",
      "status": "partial",
      "pages": 18,
      "processed_pages": [1, 2, 3, 4, 5, 6, 8, 9],
      "failed_pages": [7],
      "fragments": [],
      "warnings": ["OCR_LOW_CONFIDENCE: page 7"]
    }
  ],
  "error": null
}
```

RAG индексирует только обработанные фрагменты и переводит файл в `review_required`.

## 7. Структурированная ошибка

Вместо строки:

```json
{"error": "Parser failed"}
```

передавать объект:

```json
{
  "error": {
    "reason_code": "UNSUPPORTED_FORMAT",
    "message": "Parser does not support this MIME type",
    "retryable": false,
    "attempt": 1
  }
}
```

Минимальные `reason_code`:

```text
SOURCE_NOT_FOUND
SOURCE_READ_ERROR
UNSUPPORTED_FORMAT
OCR_FAILED
EXTRACTION_FAILED
TABLE_EXTRACTION_FAILED
PARSER_TIMEOUT
INTERNAL_ERROR
```

## 8. Что нужно изменить в Parser/RAG

1. В фоновых моделях после согласованного перехода убрать `dialog_id`; использовать только `event_id`.
2. В синхронных моделях `dialog_id` оставить.
3. Добавить `normalized_content_hash` в `ParsedDocument`.
4. Добавить `extracted_facts` в `ParsedFragment`.
5. Сделать `fragment_id` стабильным.
6. Добавить `source_file_id` и `source_page` в provenance.
7. Добавить `processed_pages` и `failed_pages` для `partial`.

### Покрытие страниц: неизвестность не означает успешный разбор

`processed_pages` содержит только страницы с наблюдёнными блоками либо с
явным подтверждением пустоты от producer. Отсутствие текста или блоков само
по себе не подтверждает пустую страницу. `failed_pages` имеет приоритет над
наблюдёнными результатами. Необязательный список `unknown_pages` перечисляет
ожидаемые страницы без результата и без подтверждённого отказа; он не
подменяется списком ошибок.

Неизвестное общее количество (`pages: null`), противоречивые номера или
непустой `unknown_pages` дают `status: partial` и машинное предупреждение
`PAGE_COUNT_UNKNOWN`, `PAGE_COUNT_MISMATCH` или `PAGE_COVERAGE_UNKNOWN: page N`.
Пустой `unknown_pages` при `pages: null` не означает полного охвата. Наличие
блока подтверждает результат на странице, но не полноту её содержимого.
Внутренний `source_page_count` подтверждается контейнером исходного документа;
прежний `page_count`, выведенный из количества блоков, не подтверждает границу.
Для Word/TXT единица логическая, а не заявленное число печатных страниц.

Свежая и повторная выдача сохраняют одинаковые страницы, статус и
предупреждения, включая `pages: null`. Записи кеша без актуального внутреннего
`page_coverage_version` повторно разбираются при штатном запросе; прежние
отчёты нельзя повысить до нового формата без разбора. Structural profile и
`schema_version: 2.0` сохраняются.
8. Заменить строковый `error` на объект ошибки.
9. В RAG развернуть входящий lifecycle batch в отдельные задачи Parser только для событий, требующих разбора; сохранять исходный `event_id` и связь `asset_id` ↔ `s3_fileid`.
10. Проверить пачку с несколькими файлами, повторную доставку, смешанные операции и независимые результаты Parser по `event_id`, а также переход от технического `dialog_id` к контракту без него.

## Актуальное дополнение от 19.10.2026

Ранее описанные изменения сохраняются. Структурный выход, координаты,
профиль обработки и качество чертежей дополнены согласованной схемой `2.0`:
[Parser → RAG](RAG-NORMALIZER-CONTRACT-V2.md). Финальная нарезка принадлежит
RAG; Parser передаёт исходные блоки и полные таблицы без токенового усечения.

## Вложения чата как `s3_fileid` (11.11.2026)

Контракт `/internal/v1/parse` не меняется: для вложения чата RAG передаёт в
`s3_fileid` uuid вложения (голый, в нижнем регистре, без расширения). Backend
хранит такие файлы не в основном бакете, а в `chat-attachments`, исходное имя
— в метаданных объекта `filename` (URL-encoded). Раньше Parser искал uuid
только в `S3_BUCKET` и отвечал `source_not_found`.

Теперь при заданном `S3_ATTACHMENTS_BUCKET` Parser, не найдя файл в
`S3_BUCKET`, проверяет ровно `s3://<S3_ATTACHMENTS_BUCKET>/<uuid>`; тип файла
определяется по расширению имени из метаданных, иначе по сигнатуре. Любой
другой вид идентификатора (путь, `..`, расширение, верхний регистр) в бакет
вложений не попадает. По умолчанию настройка пуста; на проде нужно
`S3_ATTACHMENTS_BUCKET=chat-attachments`. Подробности — README, раздел
«Где Parser ищет файлы».

## Повёрнутые листы чертежей (11.11.2026)

Схема `2.0` не меняется. В `structured_payload.layout` фрагмента `drawing`
(скан, ветка `vision_plus_vlm`) добавлено поле `turn` — поворот листа кратно
90° против часовой (0, 90, 180, 270), которым штамп приведён в правый нижний
угол, — и при повороте `turn_source` (`osd` или `geometry`), при отказе
`turn_rejected`. Рамки областей и надписей модели (`bbox`) задаются в
системе уже повёрнутого и выправленного листа (`coordinate_reference:
deskewed_page`); при `turn != 0` они не совпадают с исходным растром без
обратного поворота. Опознание векторного чертежа учитывает `/Rotate`
страницы при поиске сетки штампа.

Скан или векторная страница, текст которой в большинстве повёрнут кратно
90° (альбомная страница без `/Rotate`), разбирается по прямо стоящему
листу: фрагменты и строки внутри них идут в порядке чтения прямого листа,
абзацы не слипаются, штамп ищется в его правом нижнем углу (у полей
векторного чертежа — категории `title_block`/`material`). Поля и схема не
меняются; `position.bbox` по-прежнему в долях страницы, как её видно
(с учётом `/Rotate`), без поворота.

## Повтор `request_id` и пропавшая задача (12.11.2026)

- Повтор `POST /internal/v1/parse/background` или `POST /internal/v1/parse` с `request_id` **готового** запроса (`completed`/`partial`) и теми же `s3_fileid` с теми же операциями и `event_id`/`dialog_id` не запускает разбор заново: фоновая ручка отвечает тем же `202` (`status: "queued"`, как и раньше), синхронная — готовым результатом. Результат берётся `GET /internal/v1/parse/results/{request_id}`.
- Повтор с `request_id` запроса, закончившегося `error`, запускает разбор заново (ретрай с тем же `request_id`).
- Повтор незавершённого запроса — `409`, как и раньше; повтор готового запроса с другим набором файлов, операцией или `event_id`/`dialog_id` — тоже `409`.
- `partial` считается готовым: многофайловый синхронный запрос, где один файл получил ошибку, повторяется с новым `request_id`.
- Если задача файла стартовала дольше `PARSE_TASK_TIME_LIMIT + PARSE_STALE_MARGIN_SECONDS` назад и результата не оставила (жёсткий лимит, OOM, SIGKILL), файл получает документ со `status: "error"` и ошибкой `PARSER_TIMEOUT` (`retryable: true`), и запрос перестаёт быть `processing`. Ошибка выставляется при чтении состояния (`GET .../results/{request_id}`), поэтому гарантия относится к режиму опроса (`RESULT_DELIVERY_TYPE=none`, по умолчанию): push-канал о таком файле не сообщает. Если настоящий результат всё же придёт позже, он заменяет ошибку.

## Текст в рамке ЕСКД и слой распознавания (12.11.2026)

Схема `2.0`, поля и ручки не меняются. Под флагами (README, «Флаги
разбора»; на проде включены) меняется состав фрагментов:

- лист векторного PDF с прозой в рамке ЕСКД (ПОК, СТО, ТУ, ТЗ, письма) или
  из одной сетки таблиц приходит фрагментами `text`/`table`, а не `drawing`
  (`DRAWING_TEXT_IN_FRAME_ENABLED`);
- «таблица» MinerU на половину листа и больше с прозой внутри приходит
  обычным текстом: многостраничная книга в рамке больше не одна таблица
  (`FRAME_TABLE_GUARD_ENABLED`);
- у скана на страницах, где MinerU дал свой текст, нет фрагментов
  `ocr_layer` из строк с уверенностью ниже 0.4
  (`OCR_LAYER_DROP_LOW_CONFIDENCE`).
- классификатор «чертёж или текст» (`DRAWING_PAGE_CLASSIFIER_ENABLED`,
  поверх `DRAWING_TEXT_IN_FRAME_ENABLED`): лист ТЗ/ПМ/ТУ с рисунком-картинкой
  и штампом текстового документа приходит текстом, рисунок — отдельным
  фрагментом; в текстовом документе картинки меньше 6 % листа (логотип,
  печать, подпись) остаются `image` и не становятся `drawing`.

После включения флагов повторный разбор даёт на таких страницах другие
`fragment_id`: он считается от содержимого фрагмента (раздел 5).

## Шум распознавания сканов (13.11.2026)

Контракт не меняется: меняется текст фрагментов растровых документов (скан, картинка). Векторные PDF не затрагиваются.
Четыре флага, все по умолчанию выключены (README, «Флаги разбора»): `OCR_WORD_FIX_ENABLED` — латиница и курсив в
русских словах по словарю моделей Tesseract; `OCR_KEEP_STRUCTURED_TABLES` — спецификация ЕСКД во весь лист остаётся
таблицей; `OCR_TABLE_LINE_MIN_CONFIDENCE` — без повтора таблицы мусорными строками через сетку; `OCR_SPLIT_WIDE_GAPS` —
разворот в две колонки читается по колонкам. В `text_layer_stats` растра добавлены `low_confidence_table_lines` и
`word_fix` (`latin_words`, `confusion_words`, `junk_tokens`).

## Полное чтение листов-картинок (13.11.2026)

Схема и поля не меняются. Два флага, оба по умолчанию выключены (README, «Флаги разбора»):

- `DRAWING_UNMEASURED_NOT_PARTIAL` — фрагмент `drawing` без измеренной полноты остаётся `review_required`, но
  документ `partial` только при реальной потере (`missing_regions`, `DRAWING_NOT_RECOGNIZED`,
  `DRAWING_SKIPPED_NO_TIME`, `DRAWING_SHEETS_SKIPPED`);
- `DRAWING_IMAGE_FULL_READ` — у входа-картинки (JPG, PNG, TIFF) первым приходит фрагмент `drawing` всего листа, и
  когда MinerU нарезал из листа виды (они остаются своими фрагментами), и когда лестница назвала лист текстом при
  рамке чертежа. В его `content.text` — весь текст листа, переписанный Qwen-VL построчно (штамп, номер листа,
  изменения, примечания, технические требования); `structured_payload.transcript_line_count` — число строк. Вместе с
  первым флагом непрочитанная область на странице с переписанным текстом не делает документ `partial`.

После включения у таких листов появляется новый фрагмент, у прочих `fragment_id` не меняются.

## Дочитывание плотного листа частями (13.11.2026)

Схема не меняется. Флаг `DRAWING_TRANSCRIBE_TILES` (по умолчанию выключен, README, «Флаги разбора») к
`DRAWING_IMAGE_FULL_READ`: если весь текст листа не помещается в ответ модели (электросхема, табличка), лист
дочитывается частями, а строки оборванного ответа сохраняются; так же — лист, на котором модель сбилась на счёт
(«QF1» … «QF1000»: хвост счёта длиннее 30 строк в оборванном ответе или 200 в целом отбрасывается); `content.text` фрагмента `drawing` листа больше не
пустеет. Новые необязательные ключи `structured_payload`: `transcript_tiles` — сколько частей прочитано (есть
только у дочитанного листа), `transcript_complete`=`false` — часть листа не прочитана. Тогда в `missing_regions`
приходит область с `kind`=`transcript_tile`, `reason` — `transcript_cut` (ответ части оборвался на последней
глубине деления; её законченные строки в тексте есть), `transcript_not_read` (модель не ответила) или `time_budget`,
`bbox` — доли листа; лист не считается переписанным целиком, и документ `partial`.

## Примечания чертежей на растре (13.11.2026)

Контракт не меняется. `OCR_WORD_FIX_ENABLED` дополнительно читает курсив ГОСТ в примечаниях чертежей
(«Cozobopa» — «Договора», «Macca usdenua» — «Масса изделия»). Новый флаг `OCR_LAYER_DROP_REPEATED`
(по умолчанию выключен): на странице с текстом MinerU фрагменты `ocr_layer`, восстановленные из слоя
распознавания и повторяющие этот текст или собранные из графики без русских слов, не выдаются. В
`text_layer_stats` растра добавлен `dropped_repeated`. Блок без русских слов отбрасывается только на русской
странице: на английском скане он остаётся. Блок с обозначением, которого нет в тексте страницы у MinerU или
модели (код KKS «10JEB10CT001», «⌀14», «R1,5»), не отбрасывается ни по одному правилу.

## Перечитывание неразобранной таблицы скана (13.11.2026)

Схема не меняется. Флаг `TABLE_VLM_RETRY_ENABLED` (по умолчанию выключен, README, «Флаги разбора»): таблица
растра, которую раньше разбирали на обрывки строк OCR (`table_from_lines.degrade`), перечитывается Qwen-VL и
приходит фрагментом `table` с `provenance.method` = `vlm_escalation` (уровень 7) без `table_html`. Строки слоя
с новыми словами остаются текстом. В `text_layer_stats` добавлен `vlm_tables`. Не вышло — прежний исход.

## Символ U+0000 в содержимом фрагментов (13.11.2026)

Текстовый слой PDF отдаёт U+0000 на глифах без таблицы символов; чертёжная ветка делала из таких строк
примечания со значением `"\u0000\u0000\u0000\u0000"`. PostgreSQL не переводит `\u0000` в текст: в базе Normalizer
одна такая строка ломает любую выборку `content->>...` по всей таблице `chunks`, у RAG — приведение результата к jsonb.
Теперь `finalize_fragments` убирает U+0000 из `content.text`, `section_title`, полей чертежа, таблицы и
`structured_payload`; поле чертежа, значение которого состояло только из U+0000, выбрасывается. Уже записанные строки
очищаются переобработкой документа.

## Приём: ложные отказы и карантины (13.11.2026)

Контракт приёма не меняется: меняются вердикты.

- QG-2: точный дубль отклоняется, только если принятый ранее двойник ещё лежит в хранилище. Двойник удалён —
  `accept`; хранилище не ответило — `quarantine` с причиной вместо прежнего `reject`. То же для заявки на
  содержимое в Redis (`intake:hash:*`): заявку удалённого файла перехватывает новая загрузка.
- QG-4: документ жанра `drawing` с низкой уверенностью быстрого OCR (ниже `QG_OCR_BLOCK_CONFIDENCE`) или с долей
  нечитаемого выше `QG_OCR_UNREADABLE_SHARE` — `accept` с предупреждением (уверенность сохраняется), а не
  `quarantine`. Остальные жанры — без изменений.
- G-2: PDF без текстового слоя классифицируется по тексту быстрого OCR первых страниц (`GATEWAY_OCR_PROBE_PAGES`,
  по умолчанию 2, `0` — выключено; `GATEWAY_OCR_PROBE_SECONDS`, по умолчанию 60). В сигналах `text_source: "ocr"`.
  Непринимаемая категория по тексту OCR не отклоняет файл, а отправляет его на G-4 (карантин без модели).
- G-2: новые маркеры технической документации — обозначение по ГОСТ 3.1201 («ТАДУ 25290.00022»), «КТД», «КТПС»,
  «Карта ТПС», «СТО nn.nn» (без дат), «руководство по качеству».

## Трассировка десяти чертежей (13.11.2026)

Схема не меняется. Три флага, все по умолчанию выключены (README, «Флаги разбора»):

- `DRAWING_SHEET_MISSING_PAGES` — у скана чертежа в PDF лист без фрагмента `drawing` получает фрагмент `drawing`
  всего листа (как при чтении листов целиком), даже если на других листах фрагменты `drawing` уже есть.
  `fragment_id` нового фрагмента — `<doc_id>-frag-000-<лист>` (у листа 1 — `<doc_id>-frag-000`), он встаёт перед
  фрагментами своей страницы; у прочих фрагментов `fragment_id` не меняются;
- `RASTER_FRAME_THIN_LINES` — растровый детектор может назвать чертежом лист, который прежде шёл страницей текста;
  в `classification.signals` такого листа — `thin_line_frame`, `thin_line_rules`. Жанр документа и, значит,
  маршрут разбора и предлагаемый гриф у таких листов меняются;
- `DRAWING_MATERIAL_NO_TOLERANCE` — у поля `material`, прочитанного Qwen-VL, `tolerance` = `null`,
  `source_of_tolerance` = `unknown` (векторный разбор PDF не затронут);
- `DRAWING_PDF_FULL_READ` — у скана чертежа в PDF на каждой чертёжной странице первым приходит фрагмент
  `drawing` всего листа (`provenance.method` = `vision_plus_vlm` или `vlm_full_page`, `position.bbox` = весь лист)
  с текстом листа в `content.text` и `transcript_line_count` в `structured_payload`; фрагменты `drawing`
  вырезок видов приходят как раньше. Непрочитанная область на такой странице не делает документ `partial`
  (вместе с `DRAWING_UNMEASURED_NOT_PARTIAL`);
- `DRAWING_TRANSCRIPT_FIXES_OCR` — у фрагмента `text` (`mineru_ocr`, `ocr_layer`) на странице с переписанным
  текстом листа `content.text` может быть заменён строками модели; такой фрагмент несёт предупреждение
  `TEXT_FROM_VLM_TRANSCRIPT`. Если цифры в строках модели другие, текст фрагмента не заменяется: чтение модели
  дописывается второй строкой с пометкой «(вариант чтения модели, требует сверки)», предупреждение —
  `TEXT_VARIANT_FROM_VLM_TRANSCRIPT`. Состав и порядок фрагментов не меняются;
- `DRAWING_DIMENSION_FIDELITY` — значения полей чертежа и строки `content.text` приходят с восстановленной
  запятой десятичной дроби («M28x1,5», «Ra 1,6», «2+1,5»), с раскрытыми надстрочными цифрами
  отклонения и со знаком «±» там, где его сохранило второе прочтение той же надписи; два прочтения
  одного размера на одном месте листа сводятся в одно поле. Марка стали получает `category`
  `material`, и `tolerance` у неё больше не выдумывается (было `H10` у «12Х18Н10Т»). В `text_layer_stats`
  появляется `dimension_fixes` — сколько записей поправлено в тексте и ячейках MinerU.

Без флага: ответ Qwen-VL на запрос «прочитай чертёж», оборванный пределом длины, больше не разбирается как первый
вложенный объект — из списка надписей берутся все целые элементы и род листа.

## Устаревшие записи листа, прочитанного моделью целиком (13.11.2026)

Схема не меняется. Флаг `DRAWING_SUPPRESS_STALE_ON_FULL_READ` (по умолчанию выключен, README, «Флаги разбора»)
меняет состав фрагментов на странице, весь текст которой переписан Qwen-VL:

- фрагмент `text` (`mineru_ocr`, `ocr_layer`, `tesseract`) и фрагмент `table` (`mineru_table` и те же методы
  распознавания) **может не прийти**: он убран как повтор чтения модели (все его лексемы нашлись у модели) или
  как шум распознавания (у модели нет только обрывков, и обрывков в нём не меньше 0,6). Слово, значение, марка
  или код, которых у модели нет, оставляют фрагмент на месте. Фрагменты `text` текстового слоя
  (`text_layer_extraction`) и таблицы `vlm_escalation` не затрагиваются;
- у фрагмента `drawing` этой страницы в `structured_payload.stale_sources` — что убрано и что помечено:
  `{"dropped": [{"fragment_id", "type", "method", "reason"}], "marked": [... "variants"]}`,
  `reason` — `duplicate`, `ocr_noise` или `digits_differ`; `fragment_id` — тот же, что в выдаче (идентификаторы
  проставлены до ветки чертежей и пометкой варианта не меняются); предупреждение `STALE_SOURCES_SUPPRESSED`
  фрагмент листа получает только когда что-то убрано;
- у оставленной записи, цифры которой расходятся с чтением модели, в `structured_payload` появляется
  `vlm_transcript_variants` — список `{"block": "7:1", "model": "1:1"}`, предупреждение
  `TEXT_VARIANT_FROM_VLM_TRANSCRIPT` и `review_required` = `true`. Расхождение берётся при тех же цифрах и
  другом разделителе («Ra 63» и «Ra 6,3», «140» и «1:40») или в одной цифре у отношения с двоеточием («7:1» и
  «1:1»); «0,1» и «0,3» в графе допуска вариантами друг друга не считаются. Содержимое записи не меняется: оба чтения
  остаются, выбор — за потребителем;
- `fragment_id` и порядок остальных фрагментов не меняются. Документ от этого флага `partial` не становится.


## Графы основной надписи с подписями (13.11.2026)

Схема не меняется. Флаг `DRAWING_TITLE_BLOCK_PASS` (по умолчанию выключен, README, «Флаги разбора») меняет то, что
приходит в полях штампа.

Что было. `structured_payload.title_block` — свободный словарь от модели: на проверенных листах там оказывались
«12,35» и «1:4» без имени графы, а на двух листах — только «обозначение». Даты подписей, «Инв. № подл.» и
«Перв. примен.» не приходили вовсе: прежний запрос прямо велел служебные графы бланка пропускать, а боковые графы
лежат вне вырезки штампа. Строки графы изменений приходили в `tables[kind=title_block].rows`, но полями не
становились никогда.

Что стало. Ключи `structured_payload.title_block` — канонические имена граф ГОСТ 2.104 (`designation`, `name`,
`material`, `mass`, `scale`, `sheet`, `sheets`, `letter`, `organization`, `developed`, `checked`, `tech_control`,
`norm_control`, `approved`, `format`, `changes`, `inventory`, `inventory_dup`, `replaced_inventory`, `first_use`,
`reference`, `signed_date`), а не то, как их назвала модель. Поля `structured_drawing_fields` категории
`title_block` приходят с подписью графы: «Масса: 12,35», «Изм.: 2 Нов. ТАДУ.409-23». Новые необязательные ключи:
`title_block_handwritten` — те же графы, значение которых дописано от руки (поле в контракте помечено текстом
«(рукописно)» и приходит с `confidence` 0,5 вместо 0,85), и `side_column` — `bbox` колонки дополнительных граф и
признак, прочитана ли она. Даты подписей приходят при своих подписантах: «Разраб. 26.08.22; Утв. 30.09.25».
Одна и та же графа может прийти и в `title_block`, и в `title_block_handwritten` с разными значениями (печатное в
штампе и рукописное в боковой колонке) — выбрать между ними нечем, и оба сохраняются.

Обозначения. В графах `designation` и `first_use` восстанавливаются точки по ГОСТ 2.201 и код документа по
ГОСТ 2.102 («ТАДУ 421451001 C6» → «ТАДУ 421451.001 СБ», «73» → «ТЗ»), код организации латиницей — в кириллицу.
Потерянную группу цифр правило не восстанавливает и точку не выдумывает: «ТАДУ 6870000.001» остаётся как прочитано.

Потребителю. Ключи `title_block` стали латинскими — тот, кто читал русские имена граф, должен читать канонические.
Значения полей и `rows` таблицы штампа по форме не меняются.


## Лист-чертёж картинкой: чертёжный разбор вместо сплошного распознавания (13.11.2026)

Схема не меняется. Флаг `LADDER_DRAWING_OVER_OCR` (по умолчанию выключен, README, «Флаги разбора») меняет состав
фрагментов и статус документа у одиночных листов-картинок, которые растровый детектор считает чертежом.

Что было. Лестница сравнивала уровни по числу символов. MinerU возвращает лист-чертёж одной картинкой (0–24
символа), сплошное распознавание — строки Tesseract (66–2985 символов на проверенных листах), и побеждало всегда
оно: `documents.extra_data.fallback_won=true`, `chosen_strategy=plain_ocr`, все фрагменты с `review_required`, в
документе — фрагменты `text` со способом `tesseract` и один `drawing` листа целиком. Документ при этом приходил
`completed`.

Что стало. Выбирается `layout`; строки Tesseract в документ не попадают, вместо них приходят фрагменты `drawing`:
лист целиком (текст листа, поля, графы штампа, таблицы) и вырезки, которые MinerU нашёл на листе. `fallback_won=false`,
`degraded` пуст. Фрагментов `text` у такого документа может не быть вовсе — весь текст листа лежит в
`content.text` фрагмента `drawing`.

Сверка. Итог решается после чтения листа моделью и пишется в `documents.extra_data.drawing_route`:
`won`, `volume` (`chars`, `fields`, `tables`, `table_rows`, `transcript_lines`, `read`), `reserve_strategy`,
`reserve_chars`, при проигрыше — `restored_fragments`. Чертёжный разбор проигрывает, если модель не прочитала на
листе ничего или принесла меньше `LADDER_CONTENT_KEEP_RATIO` символов распознавания. Тогда фрагменты распознавания
возвращаются в документ (после остальных, все с `review_required`), `fallback_won=true`, а документ приходит
`partial` с `review_required=true` и новым предупреждением `DRAWING_ROUTE_THINNER_THAN_OCR`. У такого документа
`fallback_won=true` означает «текст распознавания возвращён в документ», а не «выбран фоллбэк»: `chosen_strategy`
остаётся `layout`, `is_fallback=false`, оценки попыток не пересчитываются. В сыром результате (`raw_parse_uri`) блоков
распознавания нет — там только выбранный уровень; возвращённые фрагменты есть в БД и в выдаче. Ключ `drawing_route`
пишется только у листов, где сверка была. Правило действует только вместе с `DRAWING_IMAGE_FULL_READ`.

Недостача в допуске. Разбор может уложиться в `LADDER_CONTENT_KEEP_RATIO` и всё равно принести меньше символов,
чем распознавание (например 2390 против 2985). Текст распознавания в этом случае не возвращается — иначе допуск не
имел бы смысла, — но недостача не замалчивается: `drawing_route.thinner_kept=true`, причина в `degraded`, документ
приходит `partial` с `review_required=true` и предупреждением `DRAWING_ROUTE_THINNER_KEPT`. Предупреждения
`DRAWING_ROUTE_THINNER_THAN_OCR` и `DRAWING_ROUTE_THINNER_KEPT` взаимно исключают друг друга.

Потребителю. Новые значения в `warnings` документа — `DRAWING_ROUTE_THINNER_THAN_OCR` (текст распознавания
возвращён) и `DRAWING_ROUTE_THINNER_KEPT` (оставлен разбор чертежа, но он короче распознавания): лист разобран
беднее, чем распознан, и заменять им ранее проиндексированный разбор того же файла не следует. Нормализатор сам сравнить с
прежним разбором не может: идентификатор документа считается от `s3_fileid`, а у каждого снимка файла он свой.

## Предел памяти GPU для MinerU закреплён в образе (13.11.2026)

Контракт и схема не меняются: это настройка окружения, на выдачу не влияет.

`Dockerfile.mineru` задаёт `MINERU_VIRTUAL_VRAM_SIZE=8`. Свой объём памяти MinerU берёт из
`get_vram()`, а тот отдаёт полную память карты: на 48 ГБ он выбирает `batch_ratio` 16, а очистку
памяти между шагами (`clean_vram`, порог ≤ 8 ГБ) не включает никогда.

Почему в образе, а не в `.env`: сервис `mineru-api` в `docker-compose.yml` берёт только якорь
`defaults`, без `app-env` с `env_file`, то есть `.env` не читает вовсе. Прежде значение
подкладывали отдельным override-файлом, который нужно было каждый раз передавать через `-f`:
контейнер, пересозданный без него, молча терял переменную. В образе значение не теряется.
Переопределяется обычным способом — `environment:` у сервиса или `-e` при запуске.

Для выката: после этой правки нужна пересборка образа `mineru-api` (к пяти ролям приложения).


## Исходное имя снимка из метаданных объекта (13.11.2026)

Контракт `/internal/v1/parse` и схема `2.0` не меняются: правка видна только
в логе разбора.

Снимок под разбор RAG кладёт ключом `rag-parser-snapshots/<хеш>/<имя>`, и имя
в ключе транслитерировано: в логе вместо настоящего имени стояло
`_____421451.003-01__4__.1_____._34_.jpg`. Теперь RAG на `put_object` снимка
пишет настоящее имя в метаданные объекта — ключ `filename`, percent-encoded
(`quote(..., safe="")`), чтобы кириллица пережила HTTP-заголовок; оба потока,
новая загрузка и переразбор, идут через одну функцию. Нормализатор для ключей
под `rag-parser-snapshots/` читает это поле (`head_object` → `Metadata`),
раскодирует и печатает в строке «исходное имя «…»».

Откат. Метаданных может не быть законно: у снимков, сделанных до правки RAG,
их нет вовсе, а пустое имя и значение длиннее 1024 байт RAG не записывает
сознательно. В любом таком случае — и при любом сбое хранилища — имя берётся
по-прежнему из `s3_fileid`, то есть из ключа снимка; «неизвестно» и пустая
строка там не появляются. Сбой `head_object` разбор не роняет и пишется в
`debug`, а не в `error`.

Цена. Не больше одного `head_object` на документ (строка лога одна), и только
для ключей под `rag-parser-snapshots/`. Файлы, приходящие реальным путём,
метаданные не запрашивают вовсе и в логе выглядят как прежде.

## Спор чертёжной ветки и распознавания решается составом, а не объёмом (14.11.2026)

Схема не меняется. Флаг `LADDER_STRUCTURE_OVER_LENGTH` (по умолчанию выключен, README, «Флаги разбора») меняет
маршрут разбора у листов-картинок с рамкой формата и снимает проверку человеком со всех признаков качества
разбора. Действует только вместе с `LADDER_DRAWING_OVER_OCR` и `DRAWING_IMAGE_FULL_READ`.

Что было. `LADDER_DRAWING_OVER_OCR` включался по жанру листа, а жанр ставит растровый детектор по числу длинных
линий и полос строк. Плотный лист со штампом и техническими требованиями выходит у него страницей текста: у
СМ1638.11.05.00.00.00 СБ.jpg рамка формата нашлась, длинных линий оказалось 2 вместо трёх при 7 полосах строк,
род листа — `text_scan`. Оговорка о сохранности тогда работала в полную силу, и `plain_ocr` с 98 символами и
оценкой 0.295 выиграл у `layout` с 0 символами и оценкой 0.465: решал не балл, а счёт символов.

Что стало. Лист, на котором детектор видит рамку формата (`signals.frame`, `signals.thin_line_frame`), достаётся
чертёжной ветке так же, как лист жанра `drawing`. После чтения листа победитель определяется составом
прочитанного (`core/ladder/structure.py`): поля листа, штамп, обозначение по ЕСКД, надписи видов и разрезов,
размерные величины. Штамп или обозначение — достаточный признак сами по себе; без них нужны минимум два поля и
хотя бы одна величина либо надпись вида. Символов при этом может быть меньше, чем у распознавания.

Состав пишется в `documents.extra_data.drawing_route.structure`: `fields`, `measured`, `title_block`,
`designation`, `view_titles`, `dimensions`, `table_rows`, `transcript_lines`, `structured`, `complete`.
Если состав есть, но лист по нему не опознан — ни штампа, ни обозначения, — разбор принимается как есть, а
признак остаётся в `drawing_route.thin_structure`. Предупреждением документа он не становится.

Проверка человеком. Признаки качества разбора больше не ставят документу `review_required`: к человеку документ
идёт за решением, которое может принять только он (куда документ относится, как называется, какая редакция
старше), а качество чтения листа лечится повторным разбором. Это касается всех признаков, включая
`DRAWING_ROUTE_THINNER_THAN_OCR` и `DRAWING_ROUTE_THINNER_KEPT`: они остаются в `warnings`, но `review_required`
по ним не выставляется. При выключенном флаге поведение прежнее.

Неполнота не замалчивается: `status` остаётся `partial`, предупреждения и `degraded` на месте, пометки отдельных
фрагментов (`needs_review`) тоже. Новые поля `documents.extra_data`: `text_incomplete` (текст документа неполон,
независимо от того, зовут ли человека) и `quality_reprocess` — список причин, которые лечатся повторным чтением
(`DRAWING_ROUTE_THINNER_THAN_OCR`, `DRAWING_ROUTE_THINNER_KEPT`, `DRAWING_ROUTE_THIN_STRUCTURE`,
`DRAWING_NOT_RECOGNIZED`, `DRAWING_SKIPPED_NO_TIME`, `DRAWING_SHEETS_SKIPPED`). По этому полю документы
отбираются на повторный разбор запросом к БД, а не руками.

Потребителю. RAG считает `partial` полным текстом, если все страницы разобраны и среди предупреждений нет ни
одного, кроме совещательных — `DRAWING_COMPLETENESS_UNKNOWN`, `DRAWING_NOT_RECOGNIZED`,
`parser_contract_dropped_invalid_extracted_facts:` (`super_rag/parser/completeness.py`), — и ставит событию
`indexed` без причины; иначе событие уходит в `review_required` с `parser_partial_result`. Нормализатор
`review_required` по качеству больше не выставляет, но предупреждения `DRAWING_ROUTE_*` из документа не убирает:
пока RAG различает полноту по именам предупреждений, а не по `review_required`, событие с таким предупреждением
по-прежнему окажется в очереди проверки на его стороне. Чтобы проверок не осталось совсем, различать полноту
нужно по `review_required` (или добавить имена `DRAWING_ROUTE_*` в совещательный список) — это правка в RAG, не
в Нормализаторе.

Скан PDF маршрут не меняет: страниц много, среди них бывает проза, и счёт символов на них меряет сохранность
честно.
